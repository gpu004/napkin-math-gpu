# GPU Napkin Math Problems

Try each problem on paper before you open its solution. Answers are one or two
significant digits: you want the right order of magnitude and the right
bottleneck, not a benchmark result. Each solution ends with the assumption
most likely to change its answer.

## Teaching constants

The mental math uses these rounded H100 numbers. They come from the measured
profile in `profiles/h100.measured.json` (Modal `H100!:2`, 2026-10-12), the
datasheet ceilings in `profiles/h100.json`, and the price record in
`prices/modal.json`. `crates/napkin/tests/readme.rs` fails if a profile or price
update moves any of them, and every `napkin` output below is generated by
`napkin readme --write PROBLEMS.md`.

| Constant | Value | Source |
| --- | ---: | --- |
| HBM bandwidth, `M` | 3 TB/s | measured device-to-device copy, 3002 GB/s |
| Dense BF16, `F` | 690 TFLOP/s | measured cuBLAS 8192³ GEMM |
| Dense BF16, datasheet | 990 TFLOP/s | half of NVIDIA's 1979 TFLOP/s sparse headline |
| HBM, datasheet | 3.35 TB/s | NVIDIA H100 SXM |
| Host → device, `P` | 54 GB/s | measured 512 MiB pinned copy, PCIe Gen5 x16 |
| Fixed cost per copy, `L_copy` | 9 μs | measured 4-byte synchronous copy, 8.8 μs |
| Kernel launch, `L_launch` | 2 μs | measured back-to-back empty kernels |
| Memory | 80 GB | the profile's label; `napkin fit` keeps 10% headroom, 72 GB usable |
| Price | $3.95/GPU-hour | `modal-h100`, dated 2026-10-12 |

GB means 10⁹ bytes and GiB means 2³⁰ bytes. Compute figures are dense unless a
problem says otherwise.

## 1. Copy versus add

An H100 holds three fp32 buffers `A`, `B`, and `C`, each 1 GiB (2²⁸ elements).
The buffers are far larger than the 50 MB L2 cache, so every byte goes to HBM.
Use `M = 3 TB/s`.

**Question:** how long do the copy `B = A` and the elementwise add `C = A + B`
take?

<details>
<summary>Solution</summary>

Count the bytes the kernel moves, not the bytes it allocates. A copy reads one
buffer and writes one; an add reads two and writes one.

```text
1 GiB      = 2³⁰ B = 1.07 × 10⁹ B = 1.07 GB
copy bytes = 2 × 1.07 GB = 2.15 GB
add bytes  = 3 × 1.07 GB = 3.2 GB
copy time  = 2.15 × 10⁹ B / 3 × 10¹² B/s ≈ 0.7 ms
add time   = 3.2 × 10⁹ B / 3 × 10¹² B/s ≈ 1.1 ms
```

**Answer:** about 0.7 ms for the copy and 1.1 ms for the add.

Two easy mistakes: charging only the 1 GiB allocation gives 0.36 ms, two to
three times too fast, and reading 1 GiB as 1 GB drops 7%. The add does 2²⁸ ≈
268M FLOPs, an intensity of 0.08 FLOP/B, so compute never matters. `--bytes`
accepts `GiB` directly:

<!-- napkin example estimate --gpu h100 --dtype fp32 --flops 0 --bytes 2GiB -->
```text
$ napkin estimate --gpu h100 --dtype fp32 --flops 0 --bytes 2GiB
H100 SXM 80GB · fp32 · measured 2026-10-12
intensity   0 FLOP/B   ridge 17 FLOP/B   memory-bound
compute     0 s
memory      720 μs
device      720 μs
total       720 μs   memory-bound
```
<!-- /napkin -->

<!-- napkin example estimate --gpu h100 --dtype fp32 --flops 268M --bytes 3GiB -->
```text
$ napkin estimate --gpu h100 --dtype fp32 --flops 268M --bytes 3GiB
H100 SXM 80GB · fp32 · measured 2026-10-12

memory      1.1 ms

total       1.1 ms   memory-bound
```

**Assumption most likely to change the answer:** that an add streams at the copy
rate. `napkin estimate` charges all HBM traffic at the measured copy bandwidth;
the measured add (`elementwise_gbps`) runs at 2794 GB/s, 7% slower.

</details>

## 2. Ten thousand tiny uploads

A service uploads 10,000 feature vectors of 4 KB each from pinned host memory to
an H100, one synchronous `cudaMemcpy` per vector. Use `L_copy = 9 μs` and
`P = 54 GB/s`.

**Question:** how long do the 10,000 uploads take, and how long would one 40 MB
copy of the same vectors packed together take?

<details>
<summary>Solution</summary>

Every synchronous copy pays the fixed cost before its bytes count:

```text
copy time   = copies × L_copy + bytes / P
10,000 sync = 10,000 × 9 μs + 40 MB / 54 GB/s = 90 ms + 0.7 ms ≈ 90 ms
1 packed    = 1 × 9 μs + 4 × 10⁷ B / 5.4 × 10¹⁰ B/s ≈ 0.7 ms
crossover   = L_copy × P = 9 μs × 54 GB/s ≈ 490 KB
```

**Answer:** about 90 ms for 10,000 copies against 0.7 ms for one packed copy,
over 100 times slower. A 4 KB copy is over 100 times smaller than the 490 KB
crossover, so it is all fixed cost.

```text
compute     0 s
memory      0 s

```
<!-- /napkin -->

<!-- napkin example estimate --gpu h100 --dtype bf16 --flops 0 --bytes 0 --h2d 40MB -->
```text
$ napkin estimate --gpu h100 --dtype bf16 --flops 0 --bytes 0 --h2d 40MB
H100 SXM 80GB · bf16 · measured 2026-10-12
```

**Assumption most likely to change the answer:** one wait per copy. Queueing
all copies asynchronously and synchronizing once (`--copy-mode async`) pays
`L_copy` once, but the per-copy cost of queueing is not measured, so napkin
prints that as a lower bound. Pageable host memory is slower still.

</details>

## 3. When does a matmul become compute-bound?

A square BF16 GEMM multiplies two N × N matrices into a third. It performs
`W = 2N³` dense FLOPs, and at best reads `A` and `B` and writes `C` once:
`Q = 3 × N² × 2 B = 6N²` bytes. Use the measured `F = 690 TFLOP/s` and
`M = 3 TB/s`.

**Question:** above what N is the GEMM compute-bound on an H100? Where would
you put the crossover if you used NVIDIA's 1979 TFLOP/s headline instead?

<details>
<summary>Solution</summary>

```text
intensity = W / Q = 2N³ / 6N² = N / 3          FLOP/B
ridge     = F / M = 690 × 10¹² / 3 × 10¹² ≈ 230  FLOP/B
N / 3     = 230  →  N ≈ 690
```

**Answer:** above N ≈ 700 by the measured numbers. The headline figure assumes
2:4 structured sparsity, which a dense matmul cannot use. With it the ridge is
`1979 / 3.35 ≈ 590 FLOP/B`, putting the crossover at N ≈ 1800 instead of
700. The dense datasheet ceiling, `990 / 3.35 ≈ 300 FLOP/B`, puts it at
N ≈ 900.

N = 512 is `2 × 512³ = 268M` FLOPs over `6 × 512² = 1.57 MB`; N = 1024 is
2.15G FLOPs over 6.29 MB:

<!-- napkin example estimate --gpu h100 --dtype bf16 --flops 268M --bytes 1.57MB -->
```text
$ napkin estimate --gpu h100 --dtype bf16 --flops 268M --bytes 1.57MB
H100 SXM 80GB · bf16 · measured 2026-10-12
intensity   170 FLOP/B   ridge 230 FLOP/B   memory-bound
compute     390 ns
memory      520 ns
device      520 ns
total       520 ns   memory-bound
```
<!-- /napkin -->

<!-- napkin example estimate --gpu h100 --dtype bf16 --flops 2.15G --bytes 6.29MB -->
```text
$ napkin estimate --gpu h100 --dtype bf16 --flops 2.15G --bytes 6.29MB
H100 SXM 80GB · bf16 · measured 2026-10-12
intensity   340 FLOP/B   ridge 230 FLOP/B   compute-bound
compute     3.1 μs
memory      2.1 μs
device      3.1 μs
total       3.1 μs   compute-bound
```
<!-- /napkin -->

`--ceiling` uses the dense datasheet numbers instead of the measured ones:

<!-- napkin example estimate --gpu h100 --dtype bf16 --flops 2.15G --bytes 6.29MB --ceiling -->
```text
$ napkin estimate --gpu h100 --dtype bf16 --flops 2.15G --bytes 6.29MB --ceiling
H100 SXM 80GB · bf16 · datasheet

memory      1.9 μs
device      2.2 μs
total       2.2 μs   compute-bound
```
<!-- /napkin -->

**Assumption most likely to change the answer:** that a small GEMM reaches the
rate measured on an 8192³ GEMM. Split into, for example, 128 × 128 output tiles,
a 1024 × 1024 output has 64 tiles for the H100's 132 SMs, so half the GPU idles
and the real time sits above both roofline terms. The ridge tells you which
ceiling binds, not what a given shape achieves.

</details>

## 4. How many requests fit?

Serve a Llama-3-8B-shaped dense model on one H100: 8B parameters, 32 layers,
8 KV heads, head dimension 128, with 16-bit weights and a 16-bit KV cache. Each
request has an 8,192-token prompt and generates 1,024 tokens. `napkin fit`
treats the H100 as 80 GB and keeps 10% headroom, leaving 72 GB usable.

**Question:** does a batch of 64 such requests fit on one H100? If not, what is
the largest batch that does?

<details>
<summary>Solution</summary>

The KV cache stores one key and one value vector per layer, KV head, and token:

```text
weights     = 8 × 10⁹ params × 16 bit / 8 = 16 GB
KV/token    = 2 × 32 layers × 8 KV heads × 128 × 2 B = 131,072 B ≈ 131 KB
per request = (8,192 + 1,024) tokens × 131 KB ≈ 1.2 GB
batch 64    = 64 × 1.2 GB ≈ 77 GB, + 16 GB weights = 93 GB > 72 GB
largest     = (72 GB − 16 GB) / 1.2 GB per request ≈ 46 requests
```

**Answer:** no; batch 64 needs about 93 GB. About 46 requests fit.

131,072 B is exactly 128 KiB but 131 KB; mixing the two units silently costs
2.4%. The same trap sits in the GPU's label: the Modal H100's
`cuDeviceTotalMem` is 85,017,624,576 B, which is 85.0 GB or 79.2 GiB, so the
"80 GB" is closer to 80 GiB. `napkin fit` multiplies 80 by 10⁹, which is
conservative by about 6%.

<!-- napkin example llm --gpu h100 --layers 32 --hidden 4096 --heads 32 --kv-heads 8 --head-dim 128 --params 8B --batch 64 --prompt 8192 --generated 1024 -->
```text
$ napkin llm --gpu h100 --layers 32 --hidden 4096 --heads 32 --kv-heads 8 --head-dim 128 --params 8B --batch 64 --prompt 8192 --generated 1024
H100 SXM 80GB · 8B params · 32 layers · 32 heads (8 KV heads, GQA 4:1) × 128 head dim · hidden 4096
weights 16-bit · KV 16-bit · activations bf16 · batch 64 × (8192 prompt + 1024 generated)

memory: what must stay resident
weights      8B × 16 / 8 = 16 GB
KV/token     2 × 32 layers × 8 KV heads × 128 × 2 B = 131 KB
live tokens  64 × (8192 + 1024) = 589824
KV cache     131 KB × 589824 = 77.3 GB
$ napkin fit --gpu h100 --params 8B --bits 16 --extra 77.3GB

prefill: one forward over 64 × 8192 = 524288 prompt tokens
linear       2 × 8B × 524288 = 8.39P FLOP
attention    2 × 32 × 32 × 128 × 64 × 8192² (causal) = 1.13P FLOP
weights      read once = 16 GB
KV write     131 KB × 524288 = 68.7 GB
activations  2 × 32 × 524288 × 4096 × 2 B (floor) = 275 GB
$ napkin estimate --gpu h100 --dtype bf16 --flops 9.51P --bytes 360GB

decode step: 64 new tokens at context 9216 (the last, largest step)
linear       2 × 8B × 64 = 1.02T FLOP
attention    4 × 32 × 32 × 128 × 64 × 9216 = 309G FLOP
weights      read once, shared by 64 requests = 16 GB
KV read      131 KB × 64 × 9216 = 77.3 GB
activations  2 × 32 × 64 × 4096 × 2 B (floor) = 33.6 MB
per token    93.3 GB / 64 = 1.46 GB
$ napkin estimate --gpu h100 --dtype bf16 --flops 1.33T --bytes 93.3GB

hypothetical: the 93.3 GB working set exceeds 72 GB usable on one H100 SXM 80GB,
so both estimates assume one GPU's bandwidth and compute. Sharding needs at least 2 GPUs;
it divides weights and KV, not per-GPU memory, and a tensor-parallel speedup needs
a communication term (napkin collective) before you claim one.
```
<!-- /napkin -->

46 requests hold `46 × 1.21 GB = 55.6 GB` of KV cache:

<!-- napkin example fit --gpu h100 --params 8B --bits 16 --extra 55.6GB -->
```text
$ napkin fit --gpu h100 --params 8B --bits 16 --extra 55.6GB
H100 SXM 80GB · 8B params · 16-bit
weights     16 GB
extra       55.6 GB
working set 71.6 GB
usable      72 GB per GPU (10% headroom)
fits        yes, on one GPU
```
<!-- /napkin -->

**Assumption most likely to change the answer:** the KV head count. With
multi-head attention, 32 KV heads instead of 8, KV/token is four times larger,
524 KB, and only 11 requests fit. An 8-bit KV cache (`--kv-bits 8`) halves it
instead. Memory every GPU keeps regardless of batch, such as the CUDA context and
activation workspace, comes on top (`--per-gpu`).

</details>

## 5. Fusing elementwise kernels

An fp16 activation `x` of 1 GB (500M elements) goes through
`y = relu(x + bias) × scale`, with per-channel `bias` and `scale` vectors whose
bytes are negligible. Unfused, that is three elementwise kernels, each reading
and writing a full tensor; fused, it is one kernel. Use `M = 3 TB/s` and
`L_launch = 2 μs`.

**Question:** how long do the unfused and fused versions take?

<details>
<summary>Solution</summary>

```text
unfused bytes = 3 kernels × (1 GB read + 1 GB write) = 6 GB
fused bytes   = 1 GB read + 1 GB write = 2 GB
unfused time  = 6 × 10⁹ B / 3 × 10¹² B/s + 3 × 2 μs ≈ 2 ms
fused time    = 2 × 10⁹ B / 3 × 10¹² B/s + 1 × 2 μs ≈ 0.7 ms
FLOPs         = 3 ops × 500M = 1.5G  →  1.5 × 10⁹ / 6 × 10⁹ = 0.25 FLOP/B
```

**Answer:** about 2 ms unfused and 0.7 ms fused, three times faster. At
0.25 FLOP/B, far below the 220 FLOP/B fp16 ridge, only bytes matter, and the launches
add microseconds.

The unfused version also allocates temporaries for `x + bias` and the `relu`
output, but that allocation is not what costs time: writing and re-reading
them is.

<!-- napkin example estimate --gpu h100 --dtype fp16 --flops 1.5G --bytes 6GB --launches 3 -->
```text
$ napkin estimate --gpu h100 --dtype fp16 --flops 1.5G --bytes 6GB --launches 3
H100 SXM 80GB · fp16 · measured 2026-10-12
intensity   0.25 FLOP/B   ridge 220 FLOP/B   memory-bound
compute     2.3 μs
memory      2 ms
device      2 ms
launch      5.1 μs
total       2 ms   memory-bound
```
<!-- /napkin -->

<!-- napkin example estimate --gpu h100 --dtype fp16 --flops 500M --bytes 2GB --launches 1 -->
```text
$ napkin estimate --gpu h100 --dtype fp16 --flops 500M --bytes 2GB --launches 1
H100 SXM 80GB · fp16 · measured 2026-10-12
intensity   0.25 FLOP/B   ridge 220 FLOP/B   memory-bound
compute     770 ns
memory      670 μs
device      670 μs
launch      1.7 μs
total       670 μs   memory-bound
```
<!-- /napkin -->

**Assumption most likely to change the answer:** that the intermediates go to
HBM. A 10 MB tensor's temporaries fit in the 50 MB L2, so the unfused version
gets closer to the fused one. Shrink further and launches dominate: at 1 MB the
fused kernel moves 2 MB in `2 × 10⁶ B / 3 × 10¹² B/s ≈ 0.7 μs`, less than one
2 μs launch.

</details>

## 6. Batching decode

Decode the model from problem 4 on one H100 with 1,024-token prompts and
1,024 generated tokens. Cost the last, largest decode step, at context 2,048:
each step reads all weights once, shared by the batch, plus every request's KV
cache. Ignore activations and attention FLOPs. Use `M = 3 TB/s` and
`F = 690 TFLOP/s`.

**Question:** how many tokens per second does one H100 generate at batch 1, and
at batch 32?

<details>
<summary>Solution</summary>

```text
KV read/request = 131 KB × 2,048 tokens ≈ 0.27 GB
batch 1         = 16 GB + 0.27 GB = 16.3 GB per step
                  16.3 × 10⁹ B / 3 × 10¹² B/s ≈ 5.4 ms → 1 / 5.4 ms ≈ 180 tokens/s
batch 32        = 16 GB + 32 × 0.27 GB = 24.6 GB per step
                  24.6 × 10⁹ B / 3 × 10¹² B/s ≈ 8.2 ms → 32 / 8.2 ms ≈ 3,900 tokens/s
FLOPs, batch 32 = 2 × 8 × 10⁹ × 32 = 512G → 512 × 10⁹ / 690 × 10¹² ≈ 0.7 ms
```

**Answer:** about 180 tokens/s at batch 1 and 3,900 tokens/s at batch 32,
20 times more. A step costs 50% more time but serves 32 times as many tokens,
because the 16 GB weight read is shared. Even at batch 32 the FLOPs take 0.7 ms
of an 8.2 ms step: decode stays memory-bound.


**Assumption most likely to change the answer:** the context length. KV reads do
not amortize across the batch: at 8,192 tokens of context each request reads
1.1 GB per step, and batch 32 reads 34 GB of KV against 16 GB of weights.

</details>

## 7. Dollars per million tokens

Take problem 6's rates, 180 and 3,900 tokens/s, on one H100 at
$3.95/GPU-hour, billed per second, busy 100% of the time with no startup or
idle time.

**Question:** what does a million generated tokens cost at batch 1, and at
batch 32?

<details>
<summary>Solution</summary>

```text
batch 1  = 180 tokens/s × 3,600 s ≈ 650K tokens per GPU-hour
           $3.95 / 0.65M tokens ≈ $6 per million tokens
batch 32 = 3,900 tokens/s × 3,600 s ≈ 14M tokens per GPU-hour
           $3.95 / 14M tokens ≈ $0.28 per million tokens
```

**Answer:** about $6 per million tokens at batch 1 and $0.28 at batch 32, 20
times cheaper. `napkin cost` reports tokens per dollar; a million divided by
that is dollars per million tokens.
